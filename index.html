OSI参照モデル

7層・各層の役割・障害分析
最重要

OSIは「7層」を上から順に覚える

Layer名称教材での役割試験で結びつけるもの
L7アプリケーション層アプリケーション固有の役割を提供ユーザーに最も近い
L6プレゼンテーション層データの表現形式を統一表現形式
L5セッション層通信の開始から終了までを提供セッション
L4トランスポート層エンドシステム間の通信の信頼性を確保ポート番号 / セグメント
L3ネットワーク層エンドシステム間の通信を提供IP / パケット / ルーター
L2データリンク層隣接したコンピューター間の通信を提供MAC / フレーム / L2スイッチ
L1物理層ネットワークの物理的な機能を提供電気信号 / ケーブル / 電波
特に出る：L7＝アプリケーション / L3＝IP / L2＝MAC / L1＝物理的な通信手段。
OSI参照モデルを理解すると、通信障害を「どのレイヤーで起きているか」に分けて分析しやすくなる。
重要

OSI と TCP/IP の対応

  • OSI L7〜L5 → TCP/IPのアプリケーション層
  • OSI L4 → トランスポート層
  • OSI L3 → ネットワーク層（インターネット層）
  • OSI L2〜L1 → ネットワークインターフェース層
OSIは7層、TCP/IPはより大きくまとめて考える。
重要

アドレスと層

L3：IPアドレスネットワーク上の「住所」
異なるネットワークまで宛先を示す
L2：MACアドレスLAN内で機器を識別
実際のフレーム転送に使用
試験用：L3＝IP、L2＝MAC、L4＝ポート番号。

DNSと名前解決

ドメイン名・IPアドレス・正引き・逆引き
最重要

DNSの役割

通信そのものはIPアドレスを使う。人が覚えやすいドメイン名をIPアドレスへ対応付ける仕組みがDNS（Domain Name System）。

DNS＝名前を住所（IP）に変える。
最重要

正引き / 逆引き

正引きドメイン名 → IPアドレス
逆引きIPアドレス → ドメイン名
正＝名前からIP / 逆＝IPから名前。
重要

DNSは階層的に調べる

教材・小テストでは、名前解決はルートDNSサーバーを起点として階層的にドメイン情報をたどる流れとして扱う。

※実際の通信ではDNSキャッシュが使われ、毎回ルートへ問い合わせるとは限らない。試験では教材の説明を優先。

基礎

ドメイン名の見方

URLでは、ホスト名とドメイン名を組み合わせてサーバーを表す。例：www.example.co.jp

DNSがなければ、利用者は基本的にIPアドレスを直接指定する必要がある。

2

メールの仕組み

SMTP・POP3・IMAP・MAPI
最重要

SMTP＝送信

Simple Mail Transfer Protocol。メールの送信やメールサーバー間の転送に使う。

SMTP＝Send（送る）と覚える。
最重要

POP3＝端末へダウンロード

Post Office Protocol version 3。サーバーから端末へメールをダウンロードして読む方式。

サーバーから削除する設定では、別端末から同じメールを見られなくなることがある。

最重要

IMAP＝サーバーで管理・同期

Internet Message Access Protocol。メールをサーバーに残して管理するため、PC・スマホなど複数端末で同じ状態を確認しやすい。

IMAP＝複数端末向き。ただしサーバー容量に注意。
重要

SMTPのポート

小テストではSMTPの標準ポートは25番。一方、メールソフトから送信サーバーへ投稿するときは587番がよく使われる。

試験：SMTP＝送信。25番 / 設定例では587番もある。
教材

MAPI

Microsoft系で使われるMessaging Application Programming Interface。Exchangeなどとの連携で利用される。

暗号化と鍵

平文・暗号文・共通鍵・公開鍵・PKI
最重要

暗号化と復号

平文を第三者に読めない暗号文へ変換するのが暗号化。暗号文を元の平文へ戻すのが復号。

最重要

共通鍵暗号方式（PSK）

送信側と受信側が同じ鍵を共有し、その鍵で暗号化・復号する。処理が高速なのが強み。

共通鍵＝同じ鍵・高速。ただし安全な鍵共有が課題。
最重要

公開鍵暗号方式（PKI）

公開鍵と秘密鍵の異なる2つの鍵を使う。教材・小テストでは「公開鍵で暗号化 → 対応する秘密鍵で復号」と覚える。

公開鍵は公開してOK / 秘密鍵は本人だけが守る。
重要

ハイブリッド暗号方式

公開鍵暗号は安全な鍵交換に向くが処理が重い。そこで、共通鍵を安全に共有した後は高速な共通鍵暗号で実データを暗号化する。

公開鍵＝鍵を安全に渡す / 共通鍵＝本番通信を高速化。

CIA：情報セキュリティの3要素

Confidentiality / Integrity / Availability
C

Confidentiality＝機密性

権限のないユーザーがアクセスできないようにすること。

例：アクセス制御、認証、暗号化。

I

Integrity＝完全性

情報が正確であり、改ざんされていないことを保証すること。

例：成績表を勝手に書き換えられない。

A

Availability＝可用性

必要な時に適切にアクセスできる状態を維持すること。

例：サーバー停止でサービスが使えない状態を防ぐ。

C＝見せない / I＝変えさせない・正しく保つ / A＝使えるようにする。

脅威・脆弱性・リスク

3つを混同しないことが最重要
最重要

脅威（Threat）

情報資産にダメージを与える存在や出来事。悪意ある攻撃だけでなく、操作ミスや災害も含む。

最重要

脆弱性（Vulnerability）

攻撃されやすいスキ・弱点。古いソフト、弱いパスワード、設定ミス、誰でも入れる場所に置いたPCなど。

最重要

リスク（Risk）

脅威が脆弱性を利用した結果、情報資産に損害が発生する可能性。

考え方

例で考える

「攻撃者」という脅威と、「弱いパスワード」という脆弱性が重なると、不正ログインというリスクが高まる。

代表的な攻撃と対策

動画で扱われた攻撃を「何をされる攻撃か」で覚える
通信

盗聴・中間者攻撃・のぞき見

盗聴は通信内容を第三者が盗み見る。MITM（中間者攻撃）は通信途中に攻撃者が入り込む。ショルダーハッキングは画面や入力内容を物理的にのぞき見る。

公共Wi-FiではHTTPS・VPNを活用し、画面の見える場所にも注意。
改ざん

データ改ざん

データやWebページの内容を不正に書き換える攻撃。教材ではバッファオーバーフローやクロスサイトスクリプティング（XSS）も関連攻撃として紹介。

なりすまし

偽装・フィッシング

メール送信元、IPアドレス、ドメイン名などを偽り、正規の相手になりすます。BEC（ビジネスメール詐欺）やフィッシング詐欺に注意。

差出人情報・リンク先URLを確認し、MFAも有効。
パスワード

ブルートフォース攻撃

考えられるパスワードのすべての組み合わせを総当たりで試す攻撃。

パスワード

クレデンシャルスタッフィング

過去に漏えいしたID・パスワードの組み合わせを別サービスへ使い回す攻撃。パスワード使い回しが危険な理由。

対策

多要素認証（MFA）

パスワードだけでなく、所持情報・生体情報など異なる種類の認証要素を2つ以上組み合わせる。

6

多層防御

1つの対策が突破される前提で防御を重ねる
最重要

なぜ複数の対策が必要？

攻撃方法は多様で、1つのセキュリティ対策だけでは防げない攻撃がある。認証、アクセス制御、暗号化、アップデート、監視、バックアップなどを組み合わせて、1か所が破られても被害を抑える。

多層防御＝「一枚の壁」ではなく「何枚も壁を重ねる」。

脅威・脆弱性・リスク

セキュリティ1から一段深く、脆弱性を中心に理解
最重要

3つの関係

脅威＝攻撃者や事故などの危険要因、脆弱性＝攻撃されやすい入口・弱点、リスク＝その組み合わせによって被害が起きる可能性。

試験用：脅威＝攻撃者 / 脆弱性＝入口 / リスク＝被害の可能性。
教材

脆弱性の3つの顔

  • 人的脆弱性：うっかりミス、ルール違反、悪意ある内部不正
  • 物理的脆弱性：端末盗難、災害への備え不足、不正な立ち入り
  • 技術的脆弱性：プログラムのバグ、設計ミス、ソフトの不具合
「経済的脆弱性」はこの3分類には含まれない。
管理

なぜ脆弱性管理が必要？

脆弱性を放置すると、攻撃成功・情報漏えい・サービス停止・信用低下につながる。基本は把握 → 評価 → 対策。

2

代表的な脆弱性と影響

侵入後に何をされるのかを理解
特権昇格

Privilege Escalation

攻撃者がいったん侵入した後、脆弱性を悪用して管理者権限など、より高い権限を取得すること。権限が上がるほどシステムを広く操作できる。

認証

認証情報の窃取

ID・パスワードなどが盗まれると、正規利用者になりすましてVPNや社内サービスへ侵入される。ネットワーク機器の脆弱性も入口になり得る。

RCE

不正プログラム実行

Remote Code Executionは、外部から送られた不正コードをサーバー等で実行される脆弱性。データ窃取・破壊、システム乗っ取り、マルウェア感染につながる。

3

アップデートとEOS/EOL

更新は基本。でも業務継続とのバランスも必要
基本

なぜアップデートする？

OSやソフトの更新は脆弱性対策・バグ修正・セキュリティ強化の基本。脆弱性の修正が公開されたら、放置するほど攻撃される時間が長くなる。

教材：アップデートはセキュリティ対策の「基本のき」。
判断

サーバーでは即更新できないことも

業務アプリとの互換性問題で、アップデート後にアプリが動かなくなる可能性がある。その場合は検証し、必要なら一時的な代替策を取る。

期限

EOS / EOL

EOS（End of Support）＝公式サポート終了。EOL（End of Life）＝製品寿命の終了。終了後は脆弱性修正やセキュリティ更新が提供されなくなり、リスクが高まる。

代替策

更新できない時の暫定対策

教材では仮想パッチ、WAF/IPS、ネットワーク隔離などを紹介。あくまで更新までの「つなぎ」と考える。

XSS（クロスサイトスクリプティング）

ブラウザで悪意あるスクリプトを実行させる攻撃
仕組み

XSSとは

脆弱なWebサイトへ悪意あるスクリプトを仕込み、罠ページやメールリンクなどから利用者を誘導。利用者がアクセスすると、ブラウザ上でスクリプトが実行される。

被害

Cookie・セッションIDの窃取

ブラウザが保存するCookieにはログイン状態を示すセッションIDが含まれることがある。盗まれると、攻撃者が利用者になりすますセッションハイジャックにつながる。

対策

出力エスケープ

「<」「>」などの特殊文字を、ブラウザが命令として解釈しない形へ変換する。表示するときに安全化するのが基本。

教材：大切なのは出力エスケープ。入力チェックだけでは不十分。
補助

CSP

Content Security Policyで、どのスクリプトを実行してよいかをブラウザに指示する。許可していないスクリプトやインラインスクリプトを制限できる。

バッファオーバーフロー

容量を超えたデータが隣のメモリを上書きする
仕組み

バッファとは

決まった大きさを持つ一時的なデータ保管領域。想定以上のデータを書き込むと容量を超えてあふれる。

攻撃

なぜ危険？

あふれたデータが隣接するメモリ領域を上書きし、プログラム異常や不正コード実行を引き起こす。管理者権限の奪取やシステム乗っ取りにもつながり得る。

防御

OSやセキュリティソフトだけでは不十分

教材では、メモリ処理が低レベルで働く場合や起動前の攻撃など、防御をすり抜ける可能性を説明。アップデートや多層防御が必要。

ガバナンスとマネジメント

「決める人」と「動かす人」の役割を分ける
最重要

ガバナンス＝方向性を決める

組織全体の方向性・方針・優先順位を決め、全員が同じ方針で動けるようにする仕組み。セキュリティ方針の最終的な責任は経営層にある。

試験用：ガバナンス＝「何を優先するかを決める」。
教材

ガバナンスが決める4つ

  • セキュリティ方針
  • 守るべき情報の優先度
  • セキュリティ体制・責任分担
  • 予算・時間・人員などのリソース
最重要

マネジメント＝方針を実行する

ガバナンスで決めた方針を現場の行動に落とし込む。具体例は設定管理・ログ点検・教育・パッチ適用・ルール遵守など。

ガバナンス＝決める / マネジメント＝動かす・実行する。
2

ISMSとPDCA

セキュリティは一度やって終わりではない
ISMS

Information Security Management System

組織が情報セキュリティを継続的に管理するためのマネジメントシステム。個人の努力だけに頼らず、ルール・人・技術・物理対策を組織として回す。

4領域

組織・人・技術・物理

  • 組織：ルール作り、体制整備
  • 人：教育、雇用契約、意識向上
  • 技術：アンチウイルス、暗号化、アクセス制御
  • 物理：入退室管理、施錠、監視カメラ
PDCA

継続改善

Plan（計画）→ Do（実行）→ Check（点検・評価）→ Act（改善）を繰り返すことで、組織のセキュリティを強くする。

ISMSは「作って終わり」ではなく、PDCAで回し続ける。
3

ISO/IEC 27001 と 27002

要求事項と具体的な管理策の違い
ISO/IEC 27001情報セキュリティ管理の要求事項を定める。組織がISMSという「管理の仕組み」をどう構築・運用するかの基準。
ISO/IEC 27002情報セキュリティの管理策と実施の指針。具体的に「どんな対策を行うか」を考えるためのガイド。
覚え方

27001＝仕組み / 27002＝具体策

教材では、27001をルールブック、27002を対策マニュアルのように説明している。27002の管理策は、組織的・人的・物理的・技術的という4カテゴリで整理される。

4

SoA（適用宣言）

採用・不採用の根拠を見える化
最重要

Statement of Applicability

ISO/IEC 27001の管理策について、どの管理策を採用するか／しないか、その理由を明確にした文書。

SoA＝「採用・不採用＋理由」の一覧。
例

採用にも不採用にも理由が必要

例：ログ管理を「過去に事故があったため再発防止として採用」。暗号化機能を「リスクが許容範囲で業務特性上適用できないため不採用」など、判断根拠を明確にする。

利用場面

透明性を確保する

監査、取引先への説明、社内報告などで利用される。教材では地図のようなものと説明され、どの対策をなぜ選んだかを追えることが重要。

5

リスク対応の4種類

Avoid・Mitigate・Transfer・Accept
回避 Avoid

リスク源をなくす

危険なサービスを利用しないなど、リスクの原因そのものを除去して発生させない。

低減 Mitigate

確率・影響を小さくする

アクセス制御、暗号化、ウイルス対策、パッチなどで、リスクの発生確率や被害の大きさを下げる。

移転 Transfer

損失を第三者へ移す

サイバー保険や契約などを利用。特に発生可能性は低いが、発生時の損害が大きいケースで合理的。

受容 Accept

残余リスクを受け入れる

対策コストとのバランスを見て、リスクが許容範囲なら特別な対策をせず受け入れる。

実務では1種類だけとは限らず、リスクの性質や重要度に合わせて複数の対応を組み合わせる。
6

PDCAのCheckとActを止めない

教材で強調されていた「改善が止まる原因」
止まる原因

3つの典型

  • 点検・改善の記録がない
  • 何から直すか優先順位が不明
  • 担当者があいまい
危険

改善を止めると脆弱性が残る

パッチが公開されても改善が進まず脆弱性を放置すると、攻撃者にとって格好の入口になる。

改善

KPIとチェックリスト

例：パッチ適用率などのKPIで状況を数値化し、チェックリストで確認を標準化する。小さな改善を継続することが大切。
